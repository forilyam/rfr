# rfr-auth

Инструкции действуют внутри `rfr-auth` в дополнение к [корневому AGENTS.md](../AGENTS.md). Описание протоколов, endpoints и сценариев — в [README.md](README.md).

## Назначение и окружение

Сервис регистрации и аутентификации на Spring Authorization Server: Java 25, Spring Boot, Spring Security, Spring Data JPA, Thymeleaf и Flyway. Порт — 9001, схема MySQL — `rangiffler-auth`.

Сервис хранит учётные записи и права, показывает формы входа и регистрации, выдаёт токены. Профиль и дружба принадлежат `rfr-api`; интерфейс приложения — `rfr-gql-client`.

## Где вносить изменения

Пути Java-пакетов ниже указаны относительно `src/main/java/io/student/rangiffler`.

| Каталог | Ответственность |
|---|---|
| `config` | Security filter chains, OAuth, JWT claims, отзыв токенов и тема страниц |
| `controller` | MVC-обработка входа, регистрации и ошибок |
| `model`, `validation` | Форма регистрации и серверная валидация |
| `service/api`, `service/impl` | Контракты и реализация регистрации, загрузка учётных данных |
| `data`, `data/repository` | JPA-сущности учётных записей, прав и репозиторий |
| `service/cors` | Настройки доступа фронтенда |

Ресурсы находятся в `src/main/resources`: `application.yaml` — настройки, `templates` — Thymeleaf, `static` — стили, изображения и шрифты, `db/migration/rangiffler-auth` — миграции.

## Правила изменений

- Сохраняй разделение MVC, сервисов и хранения данных. Регистрация и кодирование пароля находятся в сервисе, проверка формы — в `RegistrationForm` и `validation`.
- Используй настроенный `PasswordEncoder`; не сохраняй пароль открытым текстом.
- При изменении формы согласуй серверную валидацию, имена полей шаблона и отображение ошибок. Учитывай повторную регистрацию существующего username.
- При изменении JPA-модели согласуй сущности с миграциями Flyway. Не меняй уже применённые миграции; добавляй новую.
- Не объединяй две security filter chains без отдельного согласования: OAuth/OIDC endpoints и MVC-приложение настраиваются раздельно.
- При изменении страниц сохрани обработку CSRF и поддержку светлой и тёмной темы.

## Контракт с другими модулями

- Фронтенд — публичный OAuth-клиент `client` с Authorization Code и PKCE, без client secret. Текущие callback и logout URI: `http://localhost:3001/authorized` и `http://localhost:3001/logout`.
- `AccessTokenCustomizer` добавляет в access token audience `rangiffler-api` и claim `authorities`; служебные права `FACTOR_*` отбрасываются. API ожидает права `read` и `write`.
- При изменении issuer, audience, claims, CORS или redirect URI проверяй соответствующие настройки `rfr-api` и `rfr-gql-client`.
- RSA-ключ создаётся при старте. После перезапуска ранее выданные токены становятся невалидными; для ручной проверки выполни новый вход.
- Значения TTL и адресов бери из `application.yaml`, не дублируй их в Java-коде.

## Запуск и проверка

Команды выполняются из корня репозитория; необходимы JDK 25 и MySQL на порту 3306.

```bash
./gradlew :rfr-auth:bootRun
./gradlew :rfr-auth:compileJava
```

Не запускай `localenv.sh`: он останавливает и удаляет все Docker-контейнеры машины. Для полного сценария нужны также API и фронтенд.

Перед тестовым прогоном назови конкретные тесты; запуск и остановка разрешены согласно разделу «Разрешения агента» в корневом AGENTS.md. Для изменений регистрации и входа подбирай сценарии из `rfr-e2e`; компиляция сервиса не подтверждает корректность OAuth или UI. В отчёте укажи выполненные проверки и ограничения.
