# rfr-api

Инструкции действуют внутри `rfr-api` в дополнение к [корневому AGENTS.md](../AGENTS.md). Подробности GraphQL-операций и модели — в [README.md](README.md).

## Назначение и окружение

GraphQL API на Java 25 и Spring Boot со Spring Data JPA, Flyway и OAuth Resource Server. Порт — 8081, endpoint — `/graphql`, схема MySQL — `rangiffler-api`. JWT выдаёт `rfr-auth` на порту 9001.

Профиль, страны и дружба работают с БД. Фото, лайки, лента и статистика используют JSON-моки. Моки должны оставаться в проекте до явного указания на необходимость их замены на реальные реализации.

## Где вносить изменения

Пути Java-пакетов ниже указаны относительно `src/main/java/io/student/rangiffler`.

| Каталог | Ответственность |
|---|---|
| `controller` | Query, Mutation и разрешение полей GraphQL, включая mock-контроллеры |
| `service/api`, `service/impl` | Сервисные контракты, профиль, страны и операции дружбы |
| `service/mock` | Загрузка данных mock-ленты |
| `data/entity`, `data/repository`, `data/projection` | JPA-модель, доступ к БД и проекции |
| `config` | JWT, GraphQL scalars, преобразование ошибок |
| `exception` | Ошибки предметной области |
| `util` | Существующие преобразования и адаптация пагинации |

В `src/main/resources` находятся `application.yml`, GraphQL-схема `graphql/query.graphqls`, миграции `db/migration/rangiffler-api` и JSON-моки `mock`.

## GraphQL и генерация модели

- Источник контракта — `src/main/resources/graphql/query.graphqls`. При изменении полей согласуй схему, контроллеры, сервисы и операции фронтенда.
- DGS Codegen генерирует пакет `io.student.rangiffler.model` в `build/generated/sources/dgs-codegen`. Сгенерированные файлы вручную не меняй.
- Настройки генерации и `typeMapping` находятся в `build.gradle`: connection-типы сопоставлены со Spring Data `Page`, `Date` — с `LocalDate`.
- Сохраняй действующий формат connection-ответов, пагинации и сортировки; потребители находятся в `rfr-gql-client/src/hooks`.

## Правила изменений

- Контроллеры принимают GraphQL-аргументы и передают работу сервисам. Операции с данными и транзакции оставляй в сервисном слое.
- Текущего пользователя определяй по JWT `sub`, как в существующих контроллерах. Не подменяй его идентификатором из пользовательского input.
- Учётная запись создаётся в auth, профиль API — при первом запросе текущего пользователя. Учитывай это при подготовке данных и проверке первого входа.
- При изменении дружбы учитывай направление заявки, участников и допустимые переходы ADD, ACCEPT, REJECT, DELETE.
- Изменения JPA-модели согласуй с Flyway; для изменения БД добавляй новую миграцию, не переписывай применённую.
- Не переноси JSON-моки в БД и не добавляй сохранение фото в рамках несвязанной задачи.
- Моки должны оставаться в проекте до явного указания на необходимость их замены на реальные реализации.

## Безопасность и ошибки

- JWT проверяется по issuer и audience из `application.yml`. Claim `authorities` преобразуется в права без дополнительного префикса; query требуют `read`, mutation — `write`.
- Не заменяй проверку access token использованием `id_token` и не ослабляй авторизацию ради прохождения сценария.
- HTTP 200 не гарантирует успех GraphQL-запроса: проверяй `errors` и `extensions.classification`.
- `GraphQlExceptionResolver` переводит ошибки отсутствующего ресурса в `NOT_FOUND`, недопустимого действия и аргументов — в `BAD_REQUEST`. Сохраняй согласованность с обработкой ошибок фронтенда.
- Ответ mock-мутации не доказывает сохранение. Для реальных операций подтверждай результат независимым чтением.

## Запуск и проверка

Команды выполняются из корня репозитория. Нужны MySQL и запущенный `rfr-auth`.

```bash
./gradlew :rfr-api:generateJava
./gradlew :rfr-api:compileJava
./gradlew :rfr-api:bootRun
```

После изменения схемы проверь генерацию и компиляцию, после изменения контракта — связанные хуки и типы фронтенда. Тесты запускай только после согласования конкретных тестов с пользователем. Не запускай `localenv.sh`.
