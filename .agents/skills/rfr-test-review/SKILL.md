# Ревью владения ресурсами rfr-e2e

Ресурс — всё, что тест получает и обязан вернуть: строки в БД, Page, BrowserContext. Для каждого ресурса найди владельца, момент получения, место хранения и момент освобождения; пути ниже относительны к rfr-e2e/src/test/java/io/student/rangiffler/.

## Правила

**1. Владелец — дерево декораторов.** Для @User в Store хранится только корень UserFixture из UserRequest.fixture(); Store закрывает его как AutoCloseable. UserWithRelationsFixture владеет origin, partners и своими Friendship; поля extension'а, статика и ThreadLocal ресурсами теста не владеют.

**2. Регистрация до частичной подготовки.** В UserExtension.beforeEach() put в Store должен предшествовать create(). Создание не атомарно: AuthAccount → ApiProfile → партнёры → Friendship/Invitation; close() обязан работать после падения на любом шаге, включая ещё не созданные записи.

**3. Симметрия create/close.** Декоратор удаляет ровно созданные им данные, адресно по username, в обратном порядке: свои строки → partners → origin, без широких DELETE/TRUNCATE. Проверяй цепочку через TearDown (Teardown): независимые шаги выполняются даже после ошибки, остальные ошибки сохраняются через suppressed; учитывай также связи, созданные сценарием через UI.

**4. Новая связь — значение Relation.** Статус Friendship, направление и метод TestUser::with… задаёт Relation; общий UserWithRelationsFixture создаёт и закрывает партнёров. Композиция живёт в UserRequest.fixture(), без нового декоратора для каждой связи, флагов в SingleUserFixture и веток подготовки в UserExtension; extension знает только UserRequest и контракт UserFixture.

**5. Один @User — один параметр и ключ.** Каждому @User соответствует один параметр TestUser и один ключ Store с индексом параметра: key(index) возвращает user-<index>. Подготовленные друзья и отправители приглашений находятся внутри TestUser и дерева фикстур, а не в отдельных параметрах; независимые участники сценария могут иметь собственные @User.

**6. Браузерными ресурсами владеет @UsePlaywright.** Page приходит параметром теста, как в test/people/FriendshipPreconditionTest; жизненный цикл Page и BrowserContext обеспечивает @UsePlaywright. Тесты и собственные extension'ы не создают и не закрывают эти ресурсы.

**7. Слои.** В `jupiter` нет SQL и локаторов. В `data` нет JUnit; из `jupiter` `data` знает только аннотацию `@User` во вторичном конструкторе `UserRequest(User)`. SQL живёт только в `data/db`, и `db` не зависит от `data`. В `test` нет локаторов и SQL.

**8. Вывод требует доказательства.** Каждый вывод подтверждай запуском пробы в jupiter/probe/UserExtensionTest с EngineTestKit, проверками exists() из db и целями Observed и Failing либо конкретной строкой кода. Сверяй имена с текущей веткой: сейчас методы БД называются exist(), а Observed и Failing отсутствуют; ReportedFixture подтверждает вызовы жизненного цикла, но не удаление строк БД. Без найденной причины изменений не предлагай, отсутствующие или незапущенные пробы отмечай как непроверенные.

## Формат ответа

Для каждого ресурса укажи: владелец, получение, хранение, освобождение.
Для каждого замечания укажи файл и строку, сценарий сбоя и воспроизведение: конкретную пробу или падающий шаг create().
Раздели доказательства на три списка: «подтверждено запуском», «по чтению кода», «не проверено».
Если дефектов нет, скажи об этом прямо и перечисли ограничения решения и проверки.
